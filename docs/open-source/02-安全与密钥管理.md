# 02 · 安全与密钥管理

> 目标：**开源不泄露、发布不被投毒、用户不被伤害。**
> 本文件分三部分：§1-§6 通用规范，§7 是**本工程特有攻击面清单**（照此逐项整改）。

---

## 1. 威胁模型速览

开源一个"在手机上执行任意工具链 + 自带 HTTP 服务 + 特权通道"的应用，资产与威胁如下：

| 资产 | 泄露/被攻破的后果 | 当前存放位置 | 状态 |
|---|---|---|---|
| 模型 API Key（DeepSeek 等） | 被盗刷，产生真实费用 | **设备端** `files/` 或用户环境变量 | ✅ 不在仓库 |
| Release 签名密钥（keystore） | 攻击者可冒名发布"官方更新" | 当前仅用 **debug 签名**（`android/app/build.gradle.kts:29`） | ⚠️ 待整改 |
| 用户工作区代码 | 隐私泄露 | `/storage/emulated/0/cc-haha`（外部存储） | ⚠️ 见 §7.5 |
| 特权 exec 通道 | 任意命令以 `shell` 身份执行 | `PrivilegedExecServer`（127.0.0.1 + 一次性 token） | ⚠️ 见 §7.3 |
| 仓库历史 | 一旦泄露则**永久可追溯**（fork 无法回收） | 本地未初始化 `.git` | ✅ 无历史包袱 |

**最大风险不是"代码写得不够安全"，而是"提交历史里带了一个 key"** ——后者不可逆。

## 2. 密钥生命周期：四个位置，一条铁律

### 2.1 铁律

> **任何真实密钥、Token、证书、私钥，永远不进 Git 仓库——包括当前提交、历史提交、测试文件、注释、示例配置、CI 日志。**

### 2.2 四个存放位置与正确做法

| 位置 | 用途 | 正确做法 | 禁止 |
|---|---|---|---|
| **开发者本机** | 本地调试 | `.env`（已 gitignore）/ `~/.gradle/gradle.properties` / 系统环境变量 | 硬编码进源码；提交 `.env` |
| **CI** | 自动构建/发布 | GitHub **Repository Secrets** + Environment 作用域 + 最小权限 `GITHUB_TOKEN` | 在 workflow 里 `echo` 出密钥（会进日志） |
| **设备端** | 用户自己的 API Key | 应用内设置界面 → 存 `files/`（私有目录）或用 Android Keystore 加密；**工作区里不要放** | 写入 `/storage/emulated/0`（其他应用在 targetSdk 28 下可读） |
| **仓库** | —— | 只放 `.env.example`（值全部为占位符或注释） | 放任何真实值 |

### 2.3 命名约定（便于扫描器识别）

统一使用这些前缀，可被 GitHub Secret Scanning 与 gitleaks 自动识别：

```
ANTHROPIC_AUTH_TOKEN=      ANTHROPIC_API_KEY=      DEEPSEEK_API_KEY=
OPENAI_API_KEY=            GITHUB_TOKEN=           GH_TOKEN=
SMARTLIB_GATEWAY_SECRET=   AZURE_OPENAI_API_KEY=
```

## 3. 四道防线（提交前 → 推送时 → 仓库侧 → 人工）

### 防线 1：`.gitignore`（第一道，也是最重要的一道）

见 `templates/.gitignore`。本工程必须覆盖：`.env*`、`*.keystore`/`*.jks`/`*.pem`/`*.key`、`local.properties`、`credentials*.json`、`signing/`。
**先落 `.gitignore`，再 `git init`** —— 顺序反了会污染历史。

### 防线 2：本地 pre-commit 扫描

```bash
# 方案 A：gitleaks（推荐，Go 单文件，无需 Node）
#   安装：从 Release 下载 gitleaks 二进制（GitHub 不通时可从镜像取）
gitleaks detect --source . --verbose          # 全历史扫描
gitleaks protect --staged --verbose           # 暂存区扫描（pre-commit 钩子用）

# 方案 B：环境不允许装工具时，用 grep 兜底（覆盖 80% 场景）
git diff --cached -U0 | grep -nE \
  '(sk-[A-Za-z0-9]{16,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----)' \
  && echo "❌ 检出疑似密钥，已阻止提交" && exit 1 || echo "✅ 未检出密钥"
```

把上述脚本放到 `.git/hooks/pre-commit`（或 `tools/hooks/pre-commit` 并安装），确保**每个开发者**都启用。

> 本工程 `tools/` 目录建议新增 `check-secrets.mjs`，与既有的 `tools/*.mjs` 风格一致，且可在 CI 与本地共用（Node 24 已就绪，无需额外依赖）。

### 防线 3：仓库侧（GitHub 提供，公共仓库免费）

| 功能 | 路径 | 作用 |
|---|---|---|
| **Secret Scanning** | Settings → Code security | 自动扫描已知格式的密钥；命中即告警 |
| **Push Protection** | 同上 | **在推送时直接阻断**含密钥的提交 ← 必开 |
| **Dependabot alerts** | 同上 | 依赖漏洞告警 |
| **Dependabot security updates** | 同上 | 自动提 PR 修漏洞 |
| **Code scanning (CodeQL)** | 同上 | 语义级漏洞扫描（对 Kotlin/JS 有效） |
| **Private vulnerability reporting** | 同上 | 让研究者能私密报告漏洞 ← 必开 |
| **Branch protection / Rulesets** | Settings → Branches | 禁止直接 push main、要求 PR review ← 必开 |
| **2FA** | 账号设置 | GitHub 对贡献者与维护者强制要求 |

### 防线 4：人工 Review

自动工具都有盲区（自定义格式的 Token、内部地址、个人信息）。在 `CONTRIBUTING.md` 写明：**Reviewer 必须检查 diff 中是否含凭证、内部 URL、真实 IP、用户数据**。

## 4. 泄露应急（发现密钥已进历史）

> 顺序不能反：**先轮换，再清理。** 清理历史不能撤销已经泄露的事实——互联网上的爬虫通常在分钟级抓取新提交。

```
① 立即轮换（0-10 分钟）            ← 优先级最高
   - 到服务商后台作废该 Key，签发新 Key
   - 检查账单/用量，确认是否已被滥用
② 评估影响面（10-60 分钟）
   - 该 Key 权限范围？是否可写？是否关联付费？
   - 是否同时泄露了内部地址、数据库连接串？
③ 清理历史（1 小时内）
   - 首选 git-filter-repo（官方推荐，快）：
       pip install git-filter-repo
       git filter-repo --path .env --invert-paths --force
   - 或 BFG：java -jar bfg.jar --replace-text secrets.txt repo.git
   - 清理后：git push --force --all && git push --force --tags
④ 善后（24 小时内）
   - GitHub 不会自动删除已 fork 的副本 → 联系 fork 持有者 / 走 DMCA 或支持工单
   - 若涉及用户数据 → 按当地法规评估是否需通知用户
   - 在 SECURITY.md 或 Release Notes 中说明（不必披露密钥内容）
⑤ 复盘（本周内）
   - 找到"为什么防线 1-3 没拦住"，补齐对应防线
```

**特别提示**：如果泄露的是 **Release 签名密钥**，无法"轮换"——只能①向 Google/分发渠道申请吊销；②发布迁移说明；③**最坏情况需更换包名重新发布**。所以 keystore 必须从第一天就隔离保存（见 §6）。

## 5. 依赖供应链安全

### 5.1 引入前门禁（对应 `threat-modeling` 的供应链部分）

新增任何 npm 依赖 / Termux 包 / GitHub Action 前，逐项打勾：

```
☐ 作者与维护度：是否有多个维护者？最近 12 个月是否有提交？
☐ 下载量与年龄：周下载量是否合理？（极低下载量 + 新发布 = 高怀疑度）
☐ 许可证：是否为 MIT/Apache/ISC/BSD？（AGPL/SSPL/BUSL → 直接否决）
☐ 已知漏洞：npm audit / GitHub Advisory 是否命中？
☐ 依赖树规模：是否引入数百个传递依赖？（供应链攻击面）
☐ 安装脚本：package.json 是否含 preinstall/postinstall 脚本？（警惕挖矿/窃密）
☐ 是否可替代：标准库或既有依赖能否覆盖？（能则不加）
☐ 锁文件：安装后 package-lock.json 是否已提交？
```

**本项目特别注意**：`runtime/package.json` 有 **88 个直接依赖**，`npm ls --all` 的传递依赖规模需要评估。任何一次 `npm install` 都可能引入新代码——**依赖升级必须走 PR，不得直接 push main**。

### 5.2 锁文件与可复现安装

- `package-lock.json` **必须提交**（已存在 ✅）。
- CI 与本地一律使用 `npm ci`（严格按锁文件安装），不用 `npm install`。
- Termux 工具链同理：`tools/fetch-toolchain.mjs` 应记录**索引快照版本或包版本清单**，避免"今天拉到的和昨天不一样"导致构建不可复现。

### 5.3 GitHub Actions 加固

> ⚠️ 本机 GitHub 不通（见 `reference_build_env.md`），Actions 能否用见 `03-仓库工程与发布规范.md` §6。以下为**若启用**时的硬要求。

```yaml
# ✅ 正确：固定到 commit SHA，避免 tag 被篡改
- uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608  # v4.1.0
# ❌ 错误：浮动的 tag/major，供应商被投毒即中招
- uses: actions/checkout@v4

# ✅ 最小权限
permissions:
  contents: read

# ❌ 永远不要这样做
on: pull_request_target          # 配合 checkout PR 代码 = 任意代码执行 + 密钥窃取
run: echo "${{ secrets.TOKEN }}"  # 密钥进日志
```

## 6. Release 产物安全

### 6.1 签名密钥管理（当前为 P0 缺口）

现状：`android/app/build.gradle.kts:29` 使用 `signingConfig = signingConfigs.getByName("debug")`。
**后果**：debug 签名任何人都能重新打包一个"看起来一样"的 APK；且无法通过签名验证更新来源。

整改要求：

```kotlin
// android/app/build.gradle.kts —— 从环境/属性读取，仓库内不留密钥
signingConfigs {
    create("release") {
        storeFile = file(System.getenv("CC_HAHA_KEYSTORE") ?: "release.keystore")
        storePassword = System.getenv("CC_HAHA_STORE_PASSWORD")
        keyAlias = System.getenv("CC_HAHA_KEY_ALIAS")
        keyPassword = System.getenv("CC_HAHA_KEY_PASSWORD")
    }
}
buildTypes {
    release {
        signingConfig = signingConfigs.getByName("release")   // ← 不再是 debug
        isMinifyEnabled = false
    }
}
```

```
☐ keystore 文件存放在**仓库之外**（如 D:\keys\ + 离线备份 U 盘 + 密码管理器）
☐ keystore 与密码加入 .gitignore（*.keystore, *.jks, local.properties, signing/）
☐ CI 发布时通过 Secrets 注入（Repository Secrets → environment: release）
☐ 记录密钥指纹（SHA-256）到 README，供用户校验：
      keytool -list -v -keystore release.keystore | grep SHA256
```

### 6.2 产物校验

每次 Release 必须附：

```
☐ SHA256SUMS 文件（覆盖所有上传产物）
☐ 签名指纹（APK 的 apksigner verify --print-certs 输出）
☐ 构建来源：上游 commit / RUNTIME_VERSION / 工具链快照版本
☐ 生成命令（可复制，便于第三方复现）
```

```bash
# 生成校验和
cd dist && sha256sum *.apk *.pkg > SHA256SUMS && cat SHA256SUMS
# 用户侧验证
sha256sum -c SHA256SUMS
```

### 6.3 构建环境保护

- APK 内的 `assets/*.pkg` 必须在**干净环境**生成（避免把本机临时文件、调试脚本、`.env` 打进包）。
  建议在 `tools/assemble-runtime.mjs` 中增加**打包前白名单校验**：只允许预期文件进入 `runtime.pkg`。
- 发布前解包抽查：

```bash
tar -tzf <(python -c "import gzip,sys;sys.stdout.buffer.write(gzip.open('runtime.pkg','rb').read())") | head -50
# 或按项目既有方式（runtime.pkg 为 gzip，magic 1f 8b）
```

## 7. 本项目特有攻击面清单（逐项整改）

> 这些是通用规范覆盖不到、而你的架构独有的风险点。

### 7.1 WebView 加载本地 HTTP 服务

**架构**：`WebView → http://127.0.0.1:3456 → Node 版 cc-haha server`

| 风险 | 要求 |
|---|---|
| 明文 HTTP 流量被本机其他应用嗅探 | 端口**必须**仅绑定 `127.0.0.1`（不得绑 `0.0.0.0`）；`network_security_config` 中仅对 `127.0.0.1` 放行明文 |
| 其他应用直接访问该端口调用 API | 加入**会话 Token**：App 启动时生成随机 token 注入 node，所有请求校验；WebView 通过 URL 参数或 Header 携带 |
| WebView 被诱导加载外部页面 → 可访问本地服务 | `setAllowFileAccess(false)`、`setAllowContentAccess(false)`、`setAllowFileAccessFromFileURLs(false)`、`setAllowUniversalAccessFromFileURLs(false)`；`WebViewClient.shouldOverrideUrlLoading` 中**白名单**只允许 `127.0.0.1` |
| JS 桥暴露过多能力 | `addJavascriptInterface` 的方法必须是 `@JavascriptInterface` 且**最小集**；禁止暴露文件系统任意读写 |
| 调试开启 | `WebView.setWebContentsDebuggingEnabled(false)`（release 构建）；`android:debuggable=false` |

### 7.2 工作区位于外部存储

**现状**：工作区 `/storage/emulated/0/cc-haha`；因 `targetSdk 28`，应用使用**旧版外部存储模型**（`WRITE_EXTERNAL_STORAGE` 授予广域访问）。

```
☐ 文档明确告知用户：工作区对其他应用可见（不要把密钥/隐私数据放进去）
☐ 应用内 API Key 存放**必须**在私有目录 files/，不得写在 /storage/emulated/0/cc-haha 下的任何配置里
☐ 工作区内的 CLAUDE.md 等文件不得包含 token
```

### 7.3 特权命令通道（`PrivilegedExecServer`）

**现状**：`127.0.0.1` 随机端口 + 一次性 token，`POST /exec`，以 `shell` 身份执行命令；token/port 通过 env 注入 node。

这是**最高价值的攻击目标**（从"应用内服务"升级为"shell 身份执行"）。要求：

```
☐ 端口仅绑 127.0.0.1；端口随机化（已实现 ✅）
☐ token 一次性 + 短有效期（建议 ≤ 单次会话）；用后即焚
☐ token 绝不写入日志、绝不返回给 WebView、绝不落在工作区文件里
☐ /exec 必须校验：来源 IP == 127.0.0.1、token 匹配、请求体大小上限、超时上限
☐ 命令执行采用数组形式（不拼 shell 字符串），防注入
☐ 提供**关闭开关**（用户可禁用特权通道），默认行为需明确
☐ 审计日志：记录"谁在何时执行了什么"（不含 token），保留于私有目录
☐ 文档披露：README 说明该能力的存在、用途与风险
```

### 7.4 Shizuku / Dhizuku 集成

```
☐ 仅申请**必需**的 scope，最小权限原则
☐ 首次调用前向用户说明"为什么需要 Shizuku"（UI 文案）
☐ 未授权时降级运行，不阻断主流程
☐ 不在文档中引导用户绕过系统安全机制（如 ROOT 提权教程）
```

### 7.5 `targetSdk 28` 的安全代价（必须公开披露）

| 放弃的缓解措施 | 影响 |
|---|---|
| Android 9+ 的后台限制 | 前台服务保活更容易（这正是你要的，但也是双刃剑） |
| Android 10+ 的 scoped storage | 应用可广域读写外部存储 |
| Android 10+ 的 W^X（私有目录不可 exec） | 本应用**正是为此**降级 targetSdk |
| Android 12+ 的组件导出默认关闭 | 需自行检查 `android:exported` |
| 部分网络与权限收紧策略 | 需逐版本评估 |

```
☐ README「风险披露」章节逐条说明（模板见 01 §8）
☐ 检查 AndroidManifest 中所有组件显式声明 android:exported
☐ 因 targetSdk 28 而使用 maxSdkVersion 的权限需复核（历史坑：maxSdkVersion="28"
   会让权限在 Android 12 上完全不声明——见项目记忆）
```

### 7.6 其他

```
☐ 应用内 HTTP 服务不得暴露任何"文件读取"接口给未认证调用方
☐ logcat 中不得输出 token / API Key / 用户代码内容（发布构建关闭调试日志）
☐ 调试埋点（标记文件 debug-startup-trace / debug-spawn-log）在发布构建中默认关闭 ✅（已满足），
   且文档中说明其存在与触发方式
☐ 崩溃报告不含用户代码内容
```

## 8. `SECURITY.md` 与漏洞响应

模板见 `templates/SECURITY.md`。核心要素：

| 要素 | 要求 |
|---|---|
| 报告渠道 | **Private vulnerability reporting**（GitHub 内置）或专用邮箱；**明确禁止**用公开 Issue 报安全问题 |
| 响应时限 | 承诺 48 小时内首次响应，7 天内给出评估结论 |

| 安全设计说明 | 简述 §7 的架构（本地服务、特权通道、targetSdk 权衡），帮助研究者聚焦 |
