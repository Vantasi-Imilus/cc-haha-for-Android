# 03 · 仓库工程与发布规范

> 目标：**仓库干净、构建可复现、发布可追溯、墙内可用。**
> 本项目最大的工程风险不是代码，而是 **仓库边界**——工作区 7GB，其中真正该入库的不到 1%。

---

## 1. 仓库边界：什么进，什么不进

### 1.1 决策原则

> **凡是能从"源码 + 脚本 + 版本号"重新生成的东西，一律不入库。**

按此原则对本工程逐项裁决：

| 路径 | 体积（实测） | 入库？ | 理由 / 替代方案 |
|---|---|---|---|
| `runtime/compat/`（10 个 .ts） | 小 | ✅ **入库** | 核心原创资产（Bun→Node 兼容层） |
| `tools/`（5 个脚本） | 40K | ✅ **入库** | 构建与抓取脚本 |
| `runtime/build/build.mjs` | 小 | ✅ **入库** | 打包规则（核心原创） |
| `android/`（Kotlin 壳、Gradle 脚本） | 小（除 build/ 与 assets/） | ✅ **入库** | 应用主体 |
| `build-apk.sh`、`README.md`、`PLAN.md` | 小 | ✅ **入库** | 入口与文档 |
| `runtime/package.json` + `package-lock.json` | 小 | ✅ **入库** | 依赖声明与锁文件 |
| `runtime/upstream/` | 含 2224 TS + 全量上游 | ❌ **不入库** | 上游副本；用 `tools/fetch-upstream.mjs` 按固定 commit 重建（同时满足 01 §2.3 方案 B） |
| `runtime/node_modules/` | — | ❌ 不入库 | `npm ci` 重建 |
| `runtime/dist/`、`runtime/build/` | — | ❌ 不入库 | `node build/build.mjs` 重建 |
| `runtime/*.mjs` 调试脚本（`cdp-pause*.mjs`、`cdp-test*.mjs`、`wstest.mjs`、`e2e-session-test.mjs`、`test-upgrade.mjs`） | 小 | ⚠️ **迁移后入库** | 有用但散乱 → 移到 `tools/debug/` 并加 README 说明用途；确认无用的删除 |
| `android/app/src/main/assets/*.pkg` | **346MB** | ❌ 不入库 | 由 `tools/fetch-toolchain.mjs` + `tools/assemble-runtime.mjs` 重建；或用 Release 附件分发 |
| `android/app/build/`、`android/build/`、`.gradle/` | — | ❌ 不入库 | Gradle 重建 |
| `build/`（toolchain-cache / staging） | **2.8G** | ❌ 不入库 | 中间产物 |
| `build-env/`（JDK 17 / Android SDK / Gradle 8.7） | **1.4G** | ❌ 不入库 | 文档写明版本，让贡献者自备（见 §8） |
| `*.apk` / `*.aab` | 332MB | ❌ 不入库 | Release 附件（**注意 100MB 单文件硬限制**，见 §3） |
| `cc-haha-main.zip`（父目录） | 127MB | ❌ 不在仓库内 | 位于仓库之外，无需处理；但**注意不要 `git add ..`** |

**入库总量预期**：源码 + 文档 < 20MB。若首次提交后 `git count-objects -vH` 显示超过 50MB，说明边界错了。

## 2. `.gitignore`：第一优先，先于 `git init`

模板见 `templates/.gitignore`（已按本工程定制）。三条使用纪律：

```
☐ 1. 顺序：先复制 .gitignore 到仓库根 → 再 git init → 再 git add
☐ 2. 验证：git add -A --dry-run | wc -l   （预期 < 500 个文件）
        git status --short | grep -E "\.pkg$|\.apk$|node_modules|/build/"  → 必须为空
☐ 3. 兜底：若已误提交大文件，不要用 git rm 反复折腾——
        git rm -r --cached . && git add . && git commit -m "fix: 修正仓库边界"
        （首次提交前发现=零成本；已有远程历史则须 filter-repo 重写）
```

## 3. 大文件策略（GitHub 硬限制）

| 限制 | 数值 | 对本项目的影响 |
|---|---|---|
| 单文件硬限制 | **100 MB** | `runtime.pkg`(130MB)、`toolchain-core.pkg`(206MB)、所有 `.apk` **全部超标** → 绝不能入库 |
| 仓库建议上限 | < 1 GB，最好 < 100 MB | 保持 < 20MB 即可 |
| Git LFS 免费额度 | 1 GB 存储 + 1 GB/月流量 | 346MB 的 pkg 会把额度吃掉一半以上，**不推荐用 LFS 存 pkg** |
| Release 单附件上限 | 2 GB | ✅ APK(332MB)、各 pkg 均可作为 Release 附件 |
| Release 总容量 | 无硬限制（但建议单版本 < 5GB） | ✅ |

**结论**：大文件一律走 **Release 附件**，不入 Git。在 README 提供下载与校验方式：

```markdown
## 下载

| 产物 | 大小 | 说明 |
|---|---|---|
| `cc-haha-android-vX.Y.Z.apk` | 332MB | 完整版（含预置工具链） |
| `SHA256SUMS` | 1KB | 校验和，务必核对 |

> 仓库不含大体积二进制。需自行构建见 [构建文档](#构建)。
```

## 4. 首次建仓规范

### 4.1 建仓顺序（严格照做）

```bash
cd <你的工作目录>/cc-haha-android

# ① 先落 .gitignore（从模板复制）
cp docs/open-source/templates/.gitignore .gitignore

# ② 再初始化
git init -b main
git config user.name  "Your Name"
git config user.email "you@example.com"

# ③ 预演：确认文件数量与体积
git add -A --dry-run | wc -l          # 预期 < 500
git add -A && git status --short | head -50

# ④ 提交前扫描密钥（见 02 §3 防线 2）
node tools/check-secrets.mjs || echo "停止：检出疑似密钥"

# ⑤ 首个提交
git commit -m "chore: 初始化仓库（Android 全量版 cc-haha 移植）"

# ⑥ 体检
git count-objects -vH                 # size-pack 预期 < 20 MB
git log --stat --oneline | head -20   # 确认没有意外的大文件
```

### 4.2 首个提交的粒度

建议**一个**初始提交（便于后续 `git log` 阅读），信息写清楚项目定位；不要为了"好看"拆成几十个历史伪造的提交——开源项目不需要假历史。

### 4.3 `.gitattributes`（防跨平台问题）

本工程在 Windows 开发、产物面向 Linux/Android，跨平台换行符会引发真实故障（尤其是 shell 脚本与 Python 脚本）：

```gitattributes
# 默认自动检测，提交时统一为 LF
* text=auto eol=lf

# Windows 专用脚本保留 CRLF
*.cmd text eol=crlf
*.bat text eol=crlf

# 二进制文件不做换行转换
*.pkg  binary
*.apk  binary
*.deb  binary
*.tar.gz binary
*.png  binary
*.jpg  binary
*.jar  binary
*.so   binary

# 标记为"语言统计时忽略"，避免第三方代码污染 GitHub 语言占比
runtime/upstream/**  linguist-vendored
runtime/dist/**      linguist-generated
```

## 5. 提交与分支规范

### 5.1 提交信息：Conventional Commits

```
<type>(<scope>): <subject>

type:  feat | fix | docs | style | refactor | perf | test | build | ci | chore | revert
scope: compat | android | runtime | tools | docs | deps | upstream
```

示例（贴合本项目）：

```
feat(compat): 补全 sandbox-runtime stub 的 21 个静态方法
fix(compat): bun-serve upgrade 传递原始 IncomingMessage 而非业务 Request
perf(runtime): esbuild splitting 分块 + compile cache，冷启动 5min → 20s
docs(readme): 补充 targetSdk 28 的安全权衡说明
build(tools): fetch-toolchain 记录索引快照以支持可复现构建
```

**规矩**：subject 用中文或英文均可（本项目中文语境为主），但 **type/scope 必须英文**，否则工具链（changelog 生成、语义化版本）失效。

### 5.2 分支模型（小型项目用简化 GitFlow）

```
main          —— 永远可构建、可发布；受保护，禁止直接 push
├── feat/xxx  —— 功能分支，从 main 切出，PR 合回
├── fix/xxx   —— 修复分支
└── release/vX.Y.Z —— 发布准备分支（可选，小项目直接在 main 打 tag）
```

### 5.3 分支保护规则（GitHub Rulesets）

```
☐ 禁止 force push 到 main
☐ 禁止删除 main
☐ 要求 PR 才能合并（至少 1 个 approving review）
☐ 要求状态检查通过（若启用 CI）
☐ 要求分支为最新（Require branches to be up to date）
☐ 要求 DCO 签名（若采用 DCO，见 01 §6）
☐ 禁止绕过（Include administrators = true，对自己也生效）
```

### 5.4 PR 合并策略

**Squash Merge**（推荐）：保持 `main` 历史线性，一个 PR 一条记录。
理由：本项目的贡献者多为偶发贡献，其分支内的"修正 review 意见"类提交对历史无价值。

## 6. CI/CD：墙内现实方案

> ⚠️ **前提事实**：本机 `github.com` 完全不通（见 `reference_build_env.md`）。GitHub Actions 的运行在云端（不受你的网络影响），但**你推送代码、查看结果、下载产物都受影响**。

### 6.1 三种可选路线

| 方案 | 可行性 | 成本 | 推荐度 |
|---|---|---|---|
| **A. GitHub Actions（由贡献者/云端触发）** | 你的机器推不上去，但**通过 Gitee 镜像或代理推送后**，Actions 在 GitHub 云端正常跑 | 需要解决推送通道 | ✅ 推荐（对外项目标准做法） |
| **B. 仅本地校验脚本** | 完全可行，零依赖 | 无自动化门禁，靠 review | ✅ 作为基线（必做） |
| **C. Gitee Go / 自建 Runner** | 可行（Gitee 国内可达） | 需维护 | 🟡 备选 |

**推荐组合：B 为基线 + A 为增强。**
关键设计：**把所有校验逻辑写进 `tools/verify.mjs`（本地可跑），CI 只是调用它的壳**。这样 CI 不可用时门禁不失效，贡献者也能在本地复现 CI 结果。

### 6.2 本地校验脚本契约（`tools/verify.mjs`）

```bash
node tools/verify.mjs          # 全量：密钥扫描 + lint + 构建 + 冒烟
node tools/verify.mjs --fast   # 快速：密钥扫描 + 语法检查
```

| 检查项 | 内容 | 失败即阻断 |
|---|---|---|
| 密钥扫描 | `check-secrets.mjs` | ✅ |
| 语法检查 | `node --check` 全部 `.mjs` / `tsc --noEmit`（若适用） | ✅ |
| 仓库卫生 | 禁止提交 `*.pkg`/`*.apk`/`node_modules`（检查 `git ls-files`） | ✅ |
| 兼容层构建 | `node runtime/build/build.mjs` 成功产出 | ✅ |
| 冒烟测试 | 启动服务、`curl 127.0.0.1:<port>` 返回 200 | ✅ |

### 6.3 若启用 GitHub Actions：workflow 设计

```yaml
# .github/workflows/verify.yml
name: verify
on:
  pull_request:
  push: { branches: [main] }

permissions:
  contents: read          # 最小权限

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<commit-sha>        # 固定 SHA（见 02 §5.3）
      - uses: actions/setup-node@<commit-sha>
        with: { node-version: '24' }
      - run: node tools/check-secrets.mjs
      - run: node tools/verify.mjs --fast
```

**注意**：本项目的**完整 APK 构建**（346MB 工具链 + Gradle）不适合在 GitHub 免费 Runner 上跑（超时与缓存成本）。CI 只做**源码级校验**，APK 构建保留在本地 `build-apk.sh`。

## 7. 版本与发布

### 7.1 三套版本号必须对齐

| 版本载体 | 位置 | 作用 |
|---|---|---|
| **应用版本** `versionName` / `versionCode` | `android/app/build.gradle.kts` | APK 安装/升级判定 |
| **运行时版本** `RUNTIME_VERSION` | 项目内（当前值 `"2"`） | 触发设备端运行时更新（改了 runtime 必须 +1） |
| **Git tag** `vX.Y.Z` | 仓库 | 对外发布标识 |

**纪律**：任何一次 Release，三者必须对应并在 Release Notes 中写明。改了 `compat/` 却没升 `RUNTIME_VERSION`，会导致老用户不更新运行时——这是**本项目特有的发布陷阱**。

### 7.2 语义化版本

```
主版本 MAJOR：不兼容变更（如更换运行时方案、工作区路径变更）
次版本 MINOR：向后兼容的功能（新工具链包、新界面能力）
修订号 PATCH：向后兼容的修复（compat 层 bug 修复）
```

### 7.3 CHANGELOG 与 Release Notes

`CHANGELOG.md` 用 [Keep a Changelog](https://keepachangelog.com/) 结构，按 `Added / Changed / Fixed / Removed / Security` 分类。
Release Notes 模板：

```markdown
## cc-haha Android vX.Y.Z

**产物**：`cc-haha-android-vX.Y.Z.apk`（332MB）｜ `SHA256SUMS`
**校验**：apksigner SHA-256 指纹 `xx:xx:...`（与 README 一致即为正版）
**上游**：cc-haha `@<commit>` ｜ **RUNTIME_VERSION**：`N`

### 新增 / 修复 / 变更
- …

### ⚠️ 升级提示
- 本版本修改了 runtime → 首次启动会重新解压运行时（约 1-2 分钟）
- 需 Android 12 / arm64-v8a 及以上

### 致谢
- @someone（报告 #123）
```

### 7.4 发布检查清单（每次 Release 前逐项打勾）

```
☐ versionName / versionCode / RUNTIME_VERSION 三者已对齐
☐ CHANGELOG.md 已更新
☐ 本地全量验证通过：node tools/verify.mjs
☐ Release 构建使用**正式签名**（非 debug）—— apksigner verify --print-certs 确认
☐ APK 在真机冷启动验证：安装 → 打开 → 完成一次对话（见 05 检查表的验收项）
☐ SHA256SUMS 已生成并上传
☐ 产物中不含密钥/调试文件（解包抽查 runtime.pkg）
☐ README 的下载链接与版本号已更新
☐ tag 已打：`git tag -a vX.Y.Z -m "..." && git push origin vX.Y.Z`
```

## 8. 可复现构建（贡献者上手）

**现状**：`build-env/` 未入库（1.4G），贡献者需要知道装什么。必须在 README 或 `docs/` 写清：

```markdown
## 构建环境

| 组件 | 版本 | 说明 |
|---|---|---|
| JDK | 17（BellSoft 17.0.13） | Java 26 对 AGP 过新，勿用 |
| Android SDK | platform android-31 + build-tools 34；NDK 28.2（如需） | 可用你本机的全量 SDK 安装 |

```bash
node tools/fetch-upstream.mjs      # 取得上游源码到 runtime/upstream/

./build-apk.sh

```
