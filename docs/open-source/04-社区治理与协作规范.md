# 04 · 社区治理与协作规范

> 目标：**让陌生人能贡献、让维护者不崩溃、让法务问题有出口。**
> 对个人维护的项目，最大的敌人不是"没人贡献"，而是"issue 里全是无法复现的求助"和"PR 里带进来一个密钥"。

---

## 1. 治理模型

| 阶段 | 模型 | 决策方式 | 适用信号 |
|---|---|---|---|
| **当前（0-500 star）** | BDFL（仁慈独裁者） | 项目所有者最终拍板，公开说明理由 | 贡献者 < 5 人 |
| **成长（500-5000 star）** | 核心维护者组 + 领域 owner | 2 人 approve 可合并；架构变更需 RFC | 出现稳定的活跃贡献者 |
| **成熟（>5000 star）** | 治理文档 + 选举/轮值 | 公开 RFC 流程 | —— |

**建议**：现在直接写 BDFL 模型，但**在 `CONTRIBUTING.md` 里预先声明升级路径**（"当累计 3 位贡献者各合并 ≥10 个 PR 时，邀请其成为维护者"），避免将来无据可依。

### 1.1 `CODEOWNERS`

```
# .github/CODEOWNERS
*                       @<owner>

/runtime/compat/        @<owner>      # 兼容层：架构敏感，改动需 owner review
/runtime/build/         @<owner>      # 打包规则
/android/               @<owner>      # 应用壳
/tools/                 @<owner>      # 工具链脚本
/docs/open-source/      @<owner>      # 合规文档：涉及法务，不得随意改
```

## 2. `CONTRIBUTING.md`：本项目必须写清的 8 条

模板见 `templates/CONTRIBUTING.md`。除通用内容外，本项目**必须**额外声明：

| # | 规则 | 理由 |
|---|---|---|
| 1 | **上游零修改原则**：不得直接改 `runtime/upstream/`，所有适配写在 `runtime/compat/` | 这是本项目最重要的架构决策，破坏它会导致上游无法升级 |
| 2 | **compat 层规则**：新增 stub 必须实现上游调用的**全部**静态方法 | 血泪教训——只实现"看起来够用"的几个方法，会在运行期以"静默无响应"爆雷 |
| 3 | **禁止提交二进制**：`*.pkg` / `*.apk` / `*.deb` / `node_modules` 一律拒绝 | 仓库边界（见 03 §1） |
| 4 | **禁止提交密钥**：含 `.env`、keystore、API Key、内网地址 | 见 02 §3 |
| 5 | **必须通过本地校验**：`node tools/verify.mjs --fast` | CI 可能不可用，本地校验是唯一门禁 |
| 6 | **新增依赖需说明许可证**，不得引入 AGPL/SSPL/BUSL | 见 01 §7.3 |
| 7 | **DCO 签名**：`git commit -s` | 见 01 §6 |
| 8 | **不得提交与上游授权状态相关的猜测性声明** | 法务问题一律走 §7 的升级路径 |

## 3. Issue 规范

### 3.1 模板与标签

模板文件：`templates/.github/ISSUE_TEMPLATE/{bug_report.yml,feature_request.yml}`，另建议加 `config.yml` 关闭空白 issue 并引导到 Discussions。

标签体系（在 Issues → Labels 中预建）：

| 标签 | 用途 | 颜色建议 |
|---|---|---|
| `bug` | 确认的缺陷 | 红 |
| `needs-info` | **缺复现信息，等待作者补充**（最常用的标签） | 黄 |
| `device-specific` | 与特定机型/ROM 相关 | 蓝 |
| `compat-layer` | 兼容层问题 | 紫 |
| `toolchain` | 工具链/二进制相关 | 青 |
| `security` | 安全问题 → **立即引导至私密渠道** | 深红 |
| `legal` | 授权/商标相关 → **维护者亲自处理** | 黑 |
| `wontfix` / `duplicate` / `stale` | 常规 | 灰 |

### 3.2 缺陷报告的必备信息（安卓项目特有）

本项目 90% 的"跑不起来"问题源于环境差异，因此**必须在模板中强制填写**：

```
☐ 机型与 ROM：[华为 Mate 60 / HarmonyOS 4.0（Android 12）]
☐ Android 版本与 ABI：[12 / arm64-v8a]
☐ 应用版本 + RUNTIME_VERSION：[vX.Y.Z / RUNTIME_VERSION=2]
☐ 是否安装 Shizuku/群星之眼：[是/否]
☐ workspace 路径与是否在 /storage/emulated/0：[…]
☐ 复现步骤（最小化）：[…]
☐ 期望行为 vs 实际行为：[…]
☐ 日志：logcat 过滤 TAG 输出
      adb logcat -s MainActivity ServerService:V *:S > log.txt
☐ 是否启用调试埋点（files/debug-startup-trace、files/debug-spawn-log）
```

> **无 `needs-info` 不回**：维护者给出 7 天补充期限，超时未补则关闭（模板中写明此政策，可显著减少无效 issue）。

### 3.3 响应期望（写进 README，管理预期）

```markdown
本项目由个人在业余维护，响应时间不做承诺：
- Issue：通常 3-7 天内首次回应
- PR：通常 1-2 周内 review
- 安全问题：48 小时内响应（见 SECURITY.md）
请优先查阅 docs/ 与已关闭 Issue 再提问。
```

## 4. PR 规范

### 4.1 门禁顺序

```
1. DCO 签名（每个 commit）
2. 本地已跑 `node tools/verify.mjs --fast` 并在 PR 描述中贴出结果
3. 若改的是 compat 层 → 必须附**真机验证证据**（截图/日志），不接受"理论上可行"
4. 若改的是工具链/依赖 → 附许可证说明
5. 至少 1 个维护者 approve
6. Squash merge 到 main
```

### 4.2 PR 描述的必备项

模板见 `templates/.github/pull_request_template.md`，核心是**变更类型 + 影响面 + 验证证据 + 未验证项**：

```markdown
## 变更类型
- [ ] compat 层修复  - [ ] 应用壳  - [ ] 工具链  - [ ] 文档  - [ ] 其他

## 影响面
受影响模块：…
是否影响 RUNTIME_VERSION：是/否（**若修改 runtime/，必须 +1 并说明**）

## 验证证据（必填，无证据不 review）
- 命令 + 输出：…
- 真机验证：机型 / 步骤 / 结果

## 未验证项（必填，无则写"无"）
```

> **"未验证项"是硬要求**。AI 辅助生成的 PR 尤其容易隐藏未验证部分，显式披露可大幅降低维护者排查成本。

### 4.3 明确拒绝的 PR 类型（减少双方时间浪费）

```
☐ 大规模格式化/重命名（无功能变更的重写）——除非事先在 Issue 中达成一致
☐ 修改 runtime/upstream/ 内文件
☐ 引入新的重量级依赖（尤其需联网下载模型的）
☐ 与上游授权状态相关的声明性改动（须走 §7）
☐ 提交二进制产物
```

## 5. 行为准则

采用 [Contributor Covenant v2.1](https://www.contributor-covenant.org/version/2/1/code_of_conduct/)（模板见 `templates/CODE_OF_CONDUCT.md`）。要点：

- 明确**不可接受行为**清单（人身攻击、歧视性言论、性暗示、恶意刷屏、公开他人隐私）。
- 指定**执行渠道**（专用邮箱），承诺 3 个工作日内回复。
- 说明**执行梯度**：警告 → 临时封禁 → 永久封禁。
- 中文项目建议**中英双语**，并在文件顶部注明以哪个版本为准（建议中文为准）。

## 6. 沟通渠道与语言策略

| 渠道 | 用途 | 语言 |
|---|---|---|
| GitHub Issues | 缺陷与功能请求（**唯一正式渠道**） | 中文优先，英文欢迎 |
| GitHub Discussions | 使用问答、想法、展示 | 同上 |
| README 双语 | `README.md`（中文）+ `README.en.md`（英文） | 上游已有此惯例，建议沿用 |
| 即时通讯群 | 非正式交流 | **不在仓库中放不可归档的群二维码**（会过期），改为在讨论区置顶帖维护 |

**关键原则**：**决策必须在 GitHub 上留痕**。群聊里达成的结论若未回流到 Issue/PR，等于没有决策。对个人项目而言，这直接决定半年后你还能不能看懂自己为什么这么改。

## 7. 法务与安全问题的升级路径

这是**最容易在个人项目里被忽略、后果最严重**的部分。

```
用户在 Issue/PR 中提出：

  ├─ 授权/商标/合规问题（"你们这是抄 Anthropic 的吧"）
  │    → 维护者【立即】回复："感谢指出，我们非常重视，正在核实。"
  │    → 打 `legal` 标签，【不删评、不争吵、不辩论法律细节】
  │    → 移出公开讨论（转为邮件/私密渠道），必要时临时隐藏该 Issue 的争议性内容
  │    → 咨询律师后再作正式回应；若确有问题，主动整改并公开说明
  │
  ├─ 安全问题（"我发现这个端口未鉴权"）
  │    → 【立即】回复引导至私密渠道（SECURITY.md 中的邮箱 / GitHub 私密报告）
  │    → 公开 Issue 中【不确认、不否认、不讨论细节】
  │    → 打 `security` 标签，按 SECURITY.md 的时限处理
  │
  └─ 收到 DMCA / 权利通知
       → 按 01 §2.4 的"可下架预案"执行：72 小时内响应
       → 保存所有往来记录；不要在没有法律意见的情况下提交反通知（Counter Notice）
```

**话术模板（授权质疑）**：

```markdown
感谢指出。我们非常重视授权合规问题，已记录并正在核实上游代码的来源与授权状态。
在核实完成前，本项目将暂停分发预编译产物。相关进展会在本 Issue 更新。
```

## 8. Bus Factor（个人项目最大的可持续性风险）

```
☐ 仓库所有权：至少 2 名可发布者（避免账号丢失导致项目死亡）
☐ 发布密钥：keystore 与密码有**离线备份**（U 盘/密码管理器），并写明恢复流程
☐ 架构决策留痕：所有"为什么这么做"写进 docs/ 或 PLAN.md（本项目已有 PLAN.md ✅）
☐ 上游升级路径文档化：写明如何从上游拉新版、需要重打哪些补丁（"上游零修改"设计已大幅降低此成本 ✅）
☐ 若项目停止维护：在 README 明确标注 "archived / 寻求维护者"，不要静默失联
```

## 9. 墙内可达性与镜像策略（决策 D4 落地）

事实约束：本机 `github.com` 完全不通，且国内用户下载 300MB+ APK 体验差。

```
☐ 仓库：GitHub 为主 + Gitee 镜像（手动或定期同步）
      git remote set-url --add --push origin <github-url>
      git remote set-url --add --push origin <gitee-url>     # 一次 push 双写
☐ 下载：Release 附件同时上传到 Gitee Release / 对象存储；README 提供多线路
☐ Issue：**唯一受理渠道为 GitHub**（镜像仓库的 Issue 建议在 README 说明不处理，
      避免两处跟踪导致漏单）
☐ 文档：README 纯 Markdown，不依赖需要翻墙的图片/字体 CDN（截图放仓库内 docs/images/）
☐ 依赖下载：构建脚本默认使用国内镜像（npmmirror / 阿里云 / Termux 官方源），
      已在 tools/ 中体现 ✅，需在文档中写明
```
