## 1. 权利分层模型：先搞清楚你在分发"谁的东西"

开源合规的本质是**把你要分发的每一样东西，追溯到有权授权它的人**。`cc-haha-android` 的分发物包含 5 层权利，混淆任何一层都会出事：

| 层 | 内容 | 权利人 | 许可状态 | 你的义务 |
|---|---|---|---|---|
| **L1 原创层** | `runtime/compat/`（10 个文件）、`tools/`、`android/` Kotlin 壳、`build-apk.sh`、`build.mjs` 打包规则、本目录文档 | 你 | 由你选择（见 §5） | 无（你是权利人） |
| **L2 上游层** | `runtime/upstream/` = `NanmiCoder/cc-haha` 的 `src/`、`desktop/`、`adapters/` 等 2224+ TS 文件 | 上游作者（名义上） | 上游声明 MIT，**但见 §2** | 保留上游版权与许可声明（MIT 强制） |
| **L3 npm 依赖层** | `runtime/package.json` 中 88 个 dependenc（打包进 `runtime.pkg`） | 各包作者 | 绝大多数 MIT / Apache-2.0 / ISC，**须逐包核对** | 保留许可证文本；Apache-2.0 包还需保留 NOTICE |
| **L4 二进制层** | `toolchain-core.pkg`（88 个 Termux 包）、`toolchain-android-build.pkg`、`toolchain-windows.pkg`、`hangover-wine` | 各上游开源项目（GNU/LLVM/PSF/Oracle/Wine 等） | **GPL / LGPL / Apache / PSF 混合**，见 §4 | 源码提供义务、许可证随附、LGPL 可替换性 |
| **L5 品牌层** | 名称"cc-haha"、"Claude Code"、README 表述、图标 | Anthropic 等商标权人 | 商标权与版权独立 | 非官方声明、避免混淆性使用，见 §3 |

> **关键认知**：许可证（Copyright）和商标（Trademark）是**两套独立的法律工具**。上游代码是 MIT，不等于你可以叫它"Claude Code 安卓版"。

## 2. 🔴 最高危：Anthropic Claude Code 派生代码

### 2.1 事实（已核实，附来源）

| 事实 | 来源 |
|---|---|
| 上游仓库 `NanmiCoder/cc-haha` 声明 MIT，`Copyright (c) 2026 cc-haha` | `cc-haha-main/LICENSE:1-3` |
| 上游 npm 包名为 `claude-code-local`，版本 `999.0.0-local`，`private: true`，**`repository` 字段为空** | `cc-haha-main/package.json` |
| 上游 `src/` 含 **2224 个 `.ts` 文件**，目录结构为 `QueryEngine.ts` / `Tool.ts` / `Task.ts` / `bootstrap/` / `bridge/` / `commands/` / `components/` / `coordinator/` / `daemon/` | `ls cc-haha-main/src` + `find src -name "*.ts" \| wc -l` |
| 源码使用 `import { feature } from 'bun:bundle'`（Bun 编译期特性开关）、`import ... from 'src/bootstrap/state.js'`（`src/*` 路径别名 633 处）等**非通用工程写法** | `cc-haha-main/src/QueryEngine.ts:1-8`、`runtime/build/build.mjs:21` |
| 上游 README 通篇**未出现** Anthropic 授权说明、来源声明或 "not affiliated" 免责声明（仅一处表格提 "Anthropic SDK"） | `grep -in "anthropic\|disclaimer\|免责" cc-haha-main/README.md` |
| 上游 README 自称"**Claude Code 开源桌面端**" | `cc-haha-main/README.md:4` |

**判断（⚠️ 待法律确认，非结论）**：上述结构特征与 Anthropic 官方 Claude Code CLI 的内部实现高度一致，而上游**未提供任何再许可授权链的说明**。Anthropic 的 Claude Code 以专有商业条款分发，第三方**原则上无权以 MIT 再许可**。

### 2.2 这对你意味着什么

你的工程通过以下链路**实际分发了这部分代码**：

```
runtime/upstream/src/*.ts  （上游代码副本，2224 文件）
        ↓  runtime/build/build.mjs:4,214,271  （esbuild 打包 11 个入口）
   runtime/dist/*.js  （bundle，含 cli.js）
        ↓  tools/assemble-runtime.mjs  （组装）
android/app/src/main/assets/runtime.pkg  （gzip，130,072,372 字节）
        ↓  打进 APK
app-release.apk  （332MB，已装机分发）
```

**结论**：
- 若上游无权以 MIT 授权该部分代码，则 MIT 许可证在此范围内**自始无效**（`nemo dat quod non habet`——无人能给予其所无之物）。
- 你作为**下游分发者**，即使出于善意，也可能收到下架通知（DMCA Takedown）或主张。
- **你的原创部分（L1）不受影响**——compat 层、Kotlin 壳、构建脚本是你独立完成的，风险只来自 L2 及其打包产物。

### 2.3 三种处置方案（D1 决策）

| 方案 | 做法 | 风险 | 用户获取难度 | 推荐度 |
|---|---|---|---|---|
| **A 全量开源** | 连同 `runtime/upstream/`、`runtime.pkg`、预编译 APK 一起发布 | 🔴 最高。直接再分发争议代码 + 二进制 | 最低（下载即用） | ❌ 不推荐 |
| **B 仅开源原创层** | 仓库只含 `android/` + `runtime/compat/` + `tools/` + `build.mjs`；`runtime/upstream/` 由脚本从**使用者自己的上游副本**填充；**不提供预编译 APK** | 🟢 低。你分发的是自己的代码 + 构建脚本 | 高（使用者需自行取得上游） | ✅ **推荐（作为基线）** |
| **C 全量开源但只发源码** | 代码全量（含 upstream 副本），但 **Release 不挂 APK/`*.pkg`**，只给构建说明 | 🟡 中。源码分发与二进制分发在多数司法辖区风险量级不同，但不为零 | 中 | ✅ 可与 B 组合 |

**推荐落地（B + C 组合）**：

1. **仓库主体**保留 `runtime/compat/`、`android/`、`tools/`、`build.mjs`、文档——这是你真正的心血，也是别人 fork 的价值所在。
2. `runtime/upstream/` **加入 `.gitignore`**，改用 `tools/fetch-upstream.mjs`（需新建，见 05 检查表 P0-5）：
   - 默认从 `NanmiCoder/cc-haha` 拉取**固定 commit**（保证可复现）；
   - 脚本内附提示："使用者需自行确认上游代码的授权状态"。
3. **Release 只挂"源码包 + 构建脚本 + SHA256"**，APK 由使用者自行构建；若确需分发 APK，见下方 2.4 的兜底动作。
4. README 与仓库 description 顶部加**非官方声明**（模板见 §3.3）。

### 2.4 无论选哪个方案都必须做的三件事

```
☐ 1. 非官方声明：README 首屏、仓库 About、Release 说明三处均标注
     「本项目为独立第三方开源项目，与 Anthropic PBC 无任何关联、未获其授权或背书。」

☐ 2. 来源与授权披露：新建 NOTICE 或 README 章节，明示
     「本项目在构建期使用第三方项目 NanmiCoder/cc-haha（MIT）作为上游输入，
       该上游的授权范围与来源由其作者负责。使用者应自行评估。」

☐ 3. 可下架预案（Takedown Readiness）：
     - 指定唯一对外联络邮箱（放 SECURITY.md 与 README）；
     - 承诺收到权利通知后 72 小时内响应（下架争议产物 / 移除相应代码）；
     - 预写一段下架公告模板（承诺不删库跑路，公开说明处置）；
     - 保留每次 Release 的构建来源记录（哪个上游 commit + 哪个 tag），便于精确下架。
```

> **为什么不建议"先发了再说"**：一旦仓库被 DMCA 下架，GitHub 会要求你提供反通知并提供真实身份信息，且**分叉（fork）会大量存在并难以回收**。合规成本在发布前是最低的。

## 4. Termux 二进制再分发（L4 层）

### 4.1 你在分发什么

`tools/fetch-toolchain.mjs` 从 `packages.termux.dev` 拉取 `.deb` 并解包重组，`PRESET_CORE` 清单包含：

```
python, clang, lld, binutils, git, make, cmake, ninja, pkg-config, bash,
coreutils, ripgrep, openssh, tar, xz-utils, gzip, sed, gawk, grep,
findutils, patch, …（共 88 个包，含依赖闭包）
```

另外 `toolchain-android-build.pkg` 含 OpenJDK 17 / Gradle / Kotlin / aapt2 / d8 / apksigner，`toolchain-windows.pkg` 含 llvm-mingw-w64，wine 侧含 `hangover-wine` + `wowbox64` + 117 个依赖闭包。

**这些是"二进制再分发"**，不是"链接使用"，触发完整的许可证义务。

### 4.2 义务对照（⚠️ 逐包许可待确认，核实方法见 4.4）

| 许可证族 | 典型包 | 你的义务 | 能否闭源分发 |
|---|---|---|---|
| **GPL-2.0 / GPL-3.0** | `bash`, `coreutils`, `git`, `grep`, `sed`, `gawk`, `findutils`, `tar`, `patch` ⚠️待确认 | **必须提供完整对应源码**（或书面要约 + 有效期链接）；保留许可证与版权声明；不得附加限制 | ❌ 但**你的原创代码不受传染**（进程边界调用，非链接） |
| **LGPL-2.1 / LGPL-3.0** | `hangover-wine`, `wowbox64` ⚠️待确认 | 同 GPL，**且须允许用户替换该库**（提供重链接手段或动态链接形式） | ❌ 同上 |
| **Apache-2.0** | `clang`, `lld`, `aapt2`, `d8`, `apksigner`, `gradle`, `kotlin` | 保留 LICENSE 与 **NOTICE** 文件；标注修改（若修改过） | ✅ |
| **Apache-2.0 WITH LLVM-exception** | `clang` / `lld` 的 LLVM 部分 | 同 Apache-2.0，例外条款放宽链接限制 | ✅ |
| **GPL-2.0 WITH Classpath-exception** | `openjdk-17` | 保留声明；Classpath 例外使**链接不传染** | ✅（链接使用场景） |
| **PSF-2.0** | `python` | 保留许可证与版权声明 | ✅ |
| **MIT / ISC / BSD** | `nodejs`, `ripgrep`(MIT/Unlicense), `openssh` | 保留版权与许可证文本 | ✅ |

**三个必须理解的点：**

1. **进程边界 ≠ 传染**。你的 Kotlin/TS 代码通过 `exec` 调用 GPL 二进制（如 `bash`、`git`），属于**独立进程的聚合（aggregation）**，不构成衍生作品，你的代码**无需** GPL。这是 Android 应用打包 Termux 生态的通行做法。
2. **但"打包进同一个 APK" ≠ 自动安全**。GPL 的宽松解释认为聚合不传染，但**你必须履行 GPL 的源码提供义务**——这一条与是否传染无关。
3. **LGPL 的"可替换性"是硬要求**。若 Wine 组件以动态链接库形式被你的应用加载，用户必须能替换它。你的架构是"解压到 filesDir 后 exec"，属于文件系统层面的可替换 ✅，但需在文档中明确写出这一点。

### 4.3 履行方式（最小合规动作）

```
☐ 1. 仓库根目录放 THIRD_PARTY_LICENSES.md（模板见 templates/THIRD_PARTY_LICENSES.md）
     逐包列出：包名 | 版本 | 许可证 | 上游项目主页 | 源码获取地址

☐ 2. 对 GPL/LGPL 包，提供"源码获取方式"三选一（推荐①）：
     ① 直接给出上游源码仓库与版本对应 tag 的链接（Termux 包由 Termux 构建，
        源码即上游项目源码 + Termux 构建脚本）
     ② 书面要约（Written Offer）：承诺 3 年内应请求提供源码副本
     ③ 随产物附带源码包（体积不可行，仅对自修改过的包考虑）

☐ 3. APK 内放一份许可证汇总（android/app/src/main/assets/licenses.html
     或应用内"关于 → 开源许可"页面），使**终端用户**也能看到（不只是仓库访客）

☐ 4. 若你修改过任何 GPL/LGPL 二进制（本项目未修改，仅重排布局 ✅），必须
     公开修改后的源码
```

### 4.4 待确认项与核实方法

| 待确认项 | 核实方法 |
|---|---|
| 88 个包的**逐包许可证** | 解析 `build/toolchain-cache/*.deb` 或 Termux `Packages.gz` 索引，逐个读取 `data/…/share/doc/*/copyright`（Debian 规范）或用 `licensecheck`；产出一张 CSV |
| Wine 组件的精确许可证与版本 | 读 `wine-full.tar.gz` 内 `share/licenses/` 与包元数据 |
| OpenJDK 是否含非 GPL 组件（如字体、加密扩展） | 读 `openjdk-17` 包内 `legal/` 目录 |
| 上游 `cc-haha` 是否获得 Anthropic 授权 | 直接向上游作者发 Issue 询问并**公开留痕**；同时咨询律师 |

> **建议**：新建 `tools/gen-third-party.mjs`，从 `build/toolchain-cache` 自动产出 `THIRD_PARTY_LICENSES.md`，避免手工维护漂移（见 05 检查表 P1-8）。

## 5. 许可证选型（L1 原创层，决策 D2）

### 5.1 决策矩阵

| 许可证 | 他人可否闭源商用 | 专利授权 | 商标条款 | 传染性 | 与上游 MIT 兼容 | 适合本项目？ |
|---|---|---|---|---|---|---|
| **MIT** | ✅ 可 | ❌ 无显式条款 | ❌ 无 | 无 | ✅ 完全兼容 | ✅ 最简单、与上游一致 |
| **Apache-2.0** | ✅ 可 | ✅ **显式授予** | ✅ **显式排除** | 无 | ✅ 兼容 | ✅✅ **推荐** |
| **GPL-3.0** | ❌ 必须开源 | ✅ 显式 | ✅ | 强 | ✅ | ⚠️ 会限制工具链类项目的采用 |
| **AGPL-3.0** | ❌ 含网络服务 | ✅ | ✅ | 最强 | ✅ | ❌ 过度（本项目是本地应用） |

### 5.2 推荐：Apache-2.0

**理由：**

1. **显式专利授权**（§3）：本项目涉及二进制执行、动态链接、工具链集成等可能与专利相关的领域，Apache-2.0 为下游提供明确的专利许可，降低企业用户采用顾虑。
2. **显式商标排除**（§6）：明确"本许可证不授予商标权"，与 §3 的商标规范形成闭环——这正是本项目最需要的。
3. **NOTICE 机制**：便于承载 §4 的第三方二进制归属信息。
4. 与上游 MIT **兼容**：MIT 代码可以并入 Apache-2.0 项目，只需保留原始版权声明与 MIT 全文（放入 `THIRD_PARTY_LICENSES.md` 即可）。

**若选 MIT** 也完全可行（更短、更宽松、与上游一致），但需自行在 README 补齐专利与商标声明。

### 5.3 无论选哪个，三件事必做

```
☐ 1. 仓库根目录放 LICENSE（全文，不改一字）——Apache-2.0 另需 NOTICE 文件
☐ 2. README 底部标注：License 名称 + 链接 + "Copyright (c) 2026 <你的名字/组织>"
☐ 3. 保留上游与第三方的许可证声明（新建 THIRD_PARTY_LICENSES.md）
```

> ⚠️ **不要**自创"非商业使用""仅供学习"类自定义许可证——这类许可证在法律上含义模糊、与 OSI 定义冲突，且会让 GitHub 识别失败、企业用户直接绕道。

## 6. 贡献者许可（决策 D3）

他人向你提 PR 后，你需要在**版权集中**与**贡献门槛**之间取舍：

| 方案 | 机制 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **DCO**（Developer Certificate of Origin） | 提交时 `git commit -s`，署名断言"我有权提交此代码且同意以本项目许可证分发" | 零门槛、无需系统、Linux 内核/GitLab 采用 | 版权仍分散在各贡献者手中，改许可证需逐一征得同意 | ✅ **推荐** |
| **CLA**（Contributor License Agreement） | 签署法律协议，将版权或永久许可授予项目方 | 版权集中，便于商业授权与换许可证 | 需 CLA 系统（CLA Assistant）、劝退部分贡献者 | 有商业化计划时 |

**落地方式（DCO）**：

```yaml
# .github/workflows/dco.yml 核心逻辑（伪代码）
- 检查 PR 中每个 commit 的 message 是否含 "Signed-off-by: Name <email>"
- 缺失 → PR 标记为 dco-failed，提示 `git commit --amend -s`
```

并在 `CONTRIBUTING.md` 写明：

```markdown
所有提交必须包含 DCO 签名：
```
